## 1. プロダクト概要

Nagare は、AI支援の作業をローカル優先で進めるための制御画面である。
ユーザーの自然文の依頼を Work Item(ワーク)にし、オーガナイザーが適切なエージェントに
割り当て、実行し、レビューエージェントがルーブリックで検証し、人間の判断が必要な時だけ
質問・確認・回復を求め、成果物・根拠・履歴を後から確認できるようにする。

**中心の問い(全画面がこれに答える):**

> この作業は今どうなっていて、次に自分は何をすればよいか。

## 2. 設計原則

1. **ワークが主役** — Nagare はエージェント管理画面ではなく、作業を前に進める制御画面。
2. **状態語彙は人間の行動基準** — `処理中 / 要対応・質問 / 要対応・確認 / 要対応・回復 / 完了`。
   「要対応」= あなたの入力で進む、「処理中」= 操作不要、が一目で分かる。
3. **入力ファースト** — ワーク詳細は全状態で「①状態ストリップ(いま/次)→ ②あなたへの要求
   (回答・回復選択・採否)→ ③実行の流れ(深掘り)」の順。求められている入力が最短で終わる。
4. **監査線としてのトレース** — 実行の流れは raw log ではなく「割り当ての根拠・入出力・
   使用した知識・項目別判定」を読める形で示す。診断(生ログ・内部ID・provenance)は
   明示的に開く場所へ隔離する。
5. **段階的開示** — 一覧性を優先し、詳細は折りたたみ(ルーブリック項目別判定、工程の内訳)。
   タブで同一ワークの情報を分断しない。
6. **能力の3段モデル** — スキル/MCP/実行環境は「①グローバル登録 → ②エージェント割り当て →
   ③参加プロジェクトへ自動反映」。プロジェクトへの反映は操作ではなく表示。
7. **改善は提案・プレビュー・人間の適用** — 品質記録からの改善提案は自動適用しない。
   現在→提案の比較と根拠を必ず見せる。
8. **失敗を主要フローとして扱う** — 接続テストのゲート、原因・影響・引き継ぎ付きの回復。
9. **デザインは Hachiware Labs 準拠** — 白面+slateテキスト、indigo primary、1px境界線、
   角丸8px、コンテンツ背景slate-50。色は意味(処理中=indigo、要対応=amber、回復=red、
   完了=green)にのみ使う。

## 3. 情報アーキテクチャ(左ナビ)

```
ワーク            … 唯一の日常画面(要対応ドット付き)
プロジェクト      … ワークの入れ物
分析・改善        … 評価履歴からのエージェント/基準の改善(将来)
─ エージェント ─   … 働き手と、その能力
  エージェント
  ナレッジ
  スキル
  MCP接続
  実行環境
```

一覧と詳細は別画面。ワーク詳細はタブを持たない1枚のページ。
モーダルは一時的な手続き(セットアップ、作成、確認、割り当て、提案プレビュー)のみ。

## 4. 主要オブジェクト

| オブジェクト | ユーザー向け表記 | 役割 |
| --- | --- | --- |
| Work Item | ワーク / 依頼 | 中心の作業単位。5状態を持つ |
| Project | プロジェクト | 作業フォルダ、参加エージェント、確認ポリシー既定、整理役設定 |
| Knowledge Domain | ドメイン | 複数の成果物と、それらに共通する知識・品質基準を束ねた知識体系。プロジェクト横断で共有 |
| Knowledge Artifact | 成果物 | **説明(何を・誰に・どこへ出すか)**+作成指示+評価ルーブリックの組。説明は割り当て判断と生成時に渡される。内部モデル名は互換性のため`ArtifactType`を維持する |
| Rubric | ルーブリック | 特定フォーマットのMarkdown(`## 項目名 (配点)`+判定基準本文)で一括編集。保存時に解析・検証。バージョン管理(v2→v3) |
| Agent | エージェント | オーガナイザー / ワーカー / レビュアー の3属性で作成。説明・得意分野が割り当ての材料 |
| Organizer | オーガナイザー | 内蔵の整理役。プロジェクト単位で専用エージェントに差し替え可 |
| Runtime | 実行環境 | すべてCLI経由。想定: Claude Code / Codex CLI / OpenCode / OpenClaw。検出済みのみ提示、接続テスト必須。モデル候補をエージェント設定へ提供する |
| Skill / MCP | スキル / MCP接続 | グローバルライブラリ。エージェント割り当てで有効化 |
| Artifact | できたもの | 生成・変更されたファイル |
| Evidence | 根拠 | 判定・割り当ての根拠。レビュー材料 |
| Diagnostics | 診断 | 生ログ・内部ID。明示的に開く |

### 5.9.1 改善ループの規約

| 種別 | トリガー | 生成される提案 |
| --- | --- | --- |
| 閾値(イベント) | 同一ルーブリック項目の懸念が直近5レビュー中3回 | 帰属の決まりに従いルーブリック/知識/プロンプト提案 |
| | エージェントの項目獲得率75%未満が直近5ワーク継続、または平均評価点の下降傾向 | プロンプト改善提案(そのエージェント宛) |
| | 同種の質問が3回 / 同種の差し戻し理由が2回 | 知識追記の提案 |
| | 同種の失敗(回復)が2回 | 実行環境・割り当て範囲の見直し提案 |
| 節目(リズム) | ワーク10件完了 or 週次の早い方 | ふりかえりダイジェスト(AN-9) |
| 手動 | 分析・改善画面の「今すぐ見直す」 | 上記すべてを即時評価 |

分析・提案の生成はワークの実行中には行わない(完了後のバックグラウンドで品質記録を更新)。

**2. 帰属の決まり(どこを直すか)**

- 特定のエージェントだけ低い項目 → そのエージェントの**プロンプト**
- 複数のエージェントで同じ項目が低い → **ルーブリックの判定基準**または**知識**
- 質問・差し戻しの繰り返し → **知識**(不足情報の資産化)
- 形式系の失点 → **テンプレート知識**
- 失敗の繰り返し → **実行環境・担当範囲**

**3. 適用の決まり**

- 自動適用はしない。提案は必ずDiff+根拠+プレビューを経て人間が適用する
- 1提案 = 1対象への1変更。同一対象への次の提案は、効果測定が完了するまで抑制(クールダウン: 適用後5ワークまたは2週間)
- 適用は常に新バージョンとして保存し、過去のレビュー結果に影響しない
- 受信箱は重要度順(発生頻度×失点の大きさ)で最大5件。超過分は統合または破棄

**4. 効果測定の決まり**

- 適用後、同条件の直近5ワークで前後比較(懸念件数・項目獲得率・差し戻し率)を自動表示
- 悪化した場合はロールバック提案を受信箱へ(AN-11)
- 効果測定の結果は適用履歴に常設表示(「懸念3件→0件」等)

**5. 通知と導線の決まり(知らせ → 欄 → 受信箱)**

- **受信箱(適用/却下)は分析・改善の1箇所のみ**。適用操作を他画面に分散させない
- **エージェント/ナレッジでは冒頭で「提案があること」を知らせるだけ**: 冒頭ストリップ、一覧のバッジ、
  ナビ「分析・改善」のドット(indigo=急がない。ワークのamber=要対応と色で区別)
- **知らせのリンク先は提案そのものではなく、対象(プロンプト/ルーブリック)編集画面の
  「AI支援(生成/改善案)」欄に統一**する。欄から[全文Diffを見る][受信箱へ]に進む。
  これにより導線は常に「知らせ → 欄 → 受信箱」の3段で同型になる
- ワークの実行・確認フローには改善通知を割り込ませない(記録は裏で行う)
- 適用の結果は各所有画面に反映される: ルーブリック→ナレッジ(新バージョン)、プロンプト→エージェント設定、
  知識→共通知識、確認ポリシー→プロジェクト設定と以後のワークの確認ステップ

**6. 賢くなる体感への還元**

- 差し戻しコメント・質問回答は捨てず品質記録へ(AN-12)。反復を検知したら提案に昇格し、
  「前に言ったことをまた言わされる」体験をなくす
- 実績が安定したら確認ポリシーの緩和を提案(AN-10)。改善ループの成果を
  「読む→確認する→任せる」の前進、すなわち確認の手間の減少としてユーザーに返す

### 5.10.1 トレースの記録原則 — 判断を記録し、通信は記録しない

一般的なTracer(APIコール単位のspan収集)は行わない。Nagareのトレースは
**ワーク実行の流れ=判断の記録**であり、通信の記録ではない。

**記録するもの(判断レベル · NF-2の契約対象):**

- 工程ごとの担当エージェントと割り当ての根拠
- 注入した知識・ルーブリックの参照(IDとバージョン)
- 入出力の要約(生成・変更ファイルの具体名を含む)
- 項目別のレビュー判定・根拠・懸念
- 人間の判断(質問への回答、差し戻しコメント、承認、回復の選択)
- 回復時の引き継ぎ内容(完了分・未実行分)
- 軽いメタデータ(所要時間、使用実行環境・モデル)

**記録しないもの:**

- 実行環境内部のAPIやりとり(全プロンプト・全レスポンス・トークン単位のspan)

**理由:** ①ハーネスUIと改善ループが消費するのは判断記録のみで、API spanは価値創出に寄与しない。
②ランタイム中立のため実行の中身は各実行環境が所有しており、横取り記録は技術的に脆い。
③全通信のローカル複製は機密性の表面積を不必要に広げる。

**診断への委譲:** 深掘りが必要な場合(不可解な失敗等)のために、各工程は
**実行環境側のセッションログへのポインタ**を保持する。UIの「実行の詳細ログを開く(診断)」は
このポインタを開く。生ログの保持・保護は実行環境側の責務とする。
