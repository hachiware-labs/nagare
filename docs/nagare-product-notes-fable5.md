# Nagare プロダクト所感と発展性メモ (Fable-5 UI再設計を終えて)

作成: 2026-07-05 · 文脈: Fable-5 によるUIプロトタイプ全画面(主フロー+管理領域)の再設計を完了した時点での振り返り。
プロトタイプ: `docs/design-assets/prototype/index.html`

## 1. 要件について感じたこと

### 強みと感じた点

**中心の問いの一貫性が際立っている。**
「この作業は今どうなっていて、次に自分は何をすればよいか」という単一の問いが、
画面構成・状態語彙・情報の出し分けまで貫通している。AIツールの要件は
機能列挙に流れがちだが、Nagare は「Agent管理画面ではなく作業を前に進める制御画面」
という立場を明文化しており、UIを作る側として迷いがほぼなかった。これは要件の質が高い証拠。

**状態語彙が人間の行動基準になっている。**
`処理中 / 要対応・質問 / 要対応・確認 / 要対応・回復 / 完了` は、システムの内部状態ではなく
「人間が対応すべきか」で切られている。これにより Work Home が自然に「受信箱」として機能し、
メール・タスク管理という既存習慣に接続できる。AI作業管理の学習コストを大きく下げる設計判断。

**ドメイン/ルーブリック/品質記録のループが差別化の核。**
多くのAIツールは「生成 → 人が全部読んで判断」で止まる。Nagare は評価基準(ルーブリック)を
第一級オブジェクトにし、レビューを項目別の判定+根拠として構造化し、さらに
品質記録 → 改善提案 → プレビュー → バージョン適用(v2→v3)で基準自体が育つ。
これは「組織の暗黙知が明文化されて資産になる」ループであり、使うほど良くなる
プロダクトの骨格を要件レベルで持っている。ここが Nagare の最も守るべき部分。

**失敗を前提にした運用設計。**
接続テストのゲート、回復フロー(原因・影響・引き継ぎ・回復案)、確認ポリシーの3段階
(最後に確認/重要時のみ/自動採用)。AIの実運用は失敗と信頼調整の連続であり、
それを例外処理ではなく主要フローとして要件化しているのは現実的で正しい。

### 緊張・リスクと感じた点

**概念数が多く、「中級者の崖」がある。**
Work / Project / Domain / Artifact Type / Rubric / Agent / Runtime / Skill / MCP / Evidence。
初回体験(プロジェクト+実行環境だけ)は上手く絞られているが、ユーザーが
「自分のドメインを作り、ルーブリックを書く」段階に進む瞬間に急に難しくなる。
良いルーブリックを書けるユーザーは少数派で、ここが価値の上限を決めてしまう。
→ 対策の方向: 実績からの自動下書き(品質記録→改善提案はその芽)、業種別テンプレート、
最初のレビュー結果から逆算してルーブリック案を提示する等の「作成支援」。

**dispatch(オーガナイザー)の説明責任はデータ契約に依存する。**
UIでは各工程に「割り当ての根拠」「使用した知識」を表示する設計にしたが、
これはバックエンドが判断材料を構造化して返せることが前提。
トレースのデータ契約(根拠・知識参照・ルーブリック判定の構造)を早期に固定しないと、
ハーネスUIは絵に描いた餅になる。ここは実装優先度が高い。

**スケール時の Work Home。**
数件なら現在のリスト+フィルタで十分だが、並行ワークが数十件になると
「今日対応すべきもの」の選別が次の課題になる。ダッシュボード化は要件が明示的に
避けており(正しい)、受信箱の延長(既読/スヌーズ/優先度)で解くべき。

**ローカル優先と共有資産の緊張。**
ドメイン/ルーブリックは本質的に共有したくなる資産だが、アーキテクチャはローカル優先。
エクスポート/インポートの形式を早めに決めておくと、後のチーム展開が素直になる。

## 2. 発展性

有望だと考える順に。

1. **自己改善するワークフロー(品質ループの深化)**
   現在: レビュー懸念 → 検出 → ルーブリック改善提案 → プレビュー → 適用。
   次: 同じループをエージェントのプロンプト・知識・dispatch hint にも適用する。
   さらに新旧ルーブリックの比較適用(同じ成果物を両方で評価)まで行けば、
   「使うほど品質基準が育つ」ことを定量的に示せる。Nagare の本質的な進化軸。

2. **監査可能なAI作業ハーネスとしての価値**
   実行トレース+項目別判定+根拠+Evidence は、そのまま「AI作業の監査ログ」になる。
   説明責任が問われる領域(規制業種、受託開発の検収、社内統制)では
   「AIに任せた証跡が残る」こと自体が購買理由になり得る。データは既に揃っている。

3. **ドメインパックの共有・流通**
   ドメイン(知識+成果物種別+ルーブリック)は可搬な単位。ClawHub と同じ発想で
   「法務文書パック」「技術文書パック」等の共有・配布ができると、
   中級者の崖(ルーブリックを書けない問題)を市場側から解決できる。

4. **成果物種別の一般化(文書 → コード → 定型業務)**
   Artifact Type + Rubric + Verifier(command / CI / LLM judge / rubric review)の抽象は
   文書に限らない。コードレビュー、データ処理、定型レポートへ同じ骨格で拡張できる。

5. **ランタイム中立のオーケストレーション層**
   Claude Code / Codex CLI を差し替え可能にしている構造は、
   「同じ依頼・同じルーブリックでランタイムを比較評価できる」というユニークなデータを生む。
   ランタイム選定の根拠を持てるツールは現状ほぼ存在しない。

6. **品質記録 = 組織のAI活用の成熟度メトリクス**
   どの懸念が減ったか、自動採用率がどう上がったかは、そのまま
   「この組織はAIをどこまで信頼できるようになったか」の指標になる。
   確認ポリシーの分布変化(最後に確認 → 自動採用)は経営向けの説得力あるメトリクス。

## 3. UI再設計で採った方針との対応(要点のみ)

- 実行トレースは「読めるログ」から「判断の監査線」へ: 割り当て根拠・使用知識・項目別判定を常設。
- ルーブリックは編集画面でバージョン(v2→v3)を明示し、過去レビューへ影響しないことを保証表示。
- スキル/MCP は「グローバル登録 → エージェント割り当て → 参加プロジェクトへ自動反映」の3段モデル。
  プロジェクトへの反映は操作ではなく表示(連鎖の予告)にした。
- 将来の含み: プロジェクト側の MCP 制限(オプトアウト)はモデル上追加可能だが初期UIには出さない。
