# Nagare のエージェント別 Skill 運用

## 目的

Nagare では、Skill を全エージェントが使える既定の能力として扱わず、担当する役割に必要なものだけをエージェントへ割り当てる。これにより、委譲した作業に不要な能力が混ざることを避け、利用者は「誰が、どの Skill を使って実行したか」を後から確かめられる。Skill を増やすこと自体ではなく、役割、入力、権限の境界を小さく保つことが目的である。

## Skill を割り当てる原則

割り当ては、作業の種類ではなくエージェントの継続的な責務を起点に決める。たとえば文章の設計・執筆を担うエージェントには文章作成用 Skill を割り当て、画面設計や実装のための Skill は与えない。個別の Work で一時的に必要に見える場合でも、まずその役割に本当に必要な能力かを検討する。

Skill がカタログに登録されていることと、実行中に有効であることは別である。エージェント定義で許可した Skill を候補とし、実行時に実際に読み込まれた構成を記録する。親やグローバル設定から能力が継承された場合は、意図した割り当てと区別して警告できるようにする。

## 強制ルールの責任分担

Skill の選択だけで運用を安全にすることはできない。成果物の品質や方針に関するルールは Reviewer が根拠付きで確認し、レビュー前に完了へ進めないことや必須の証跡を欠く結果を採用しないことは、Nagare の状態遷移と機械的な Verifier が担保する。さらに、特定のツールや MCP を使える範囲は、エージェント定義とランタイムアダプターで制限する。

この分担では、Reviewer の判断を重要視しつつ、破られてはならない工程上の条件をレビューだけに委ねない。誰が何を判断し、どの仕組みが実行を止められるかを分けて残すことで、失敗時の原因も追いやすくなる。

## 運用上の未解決点

当面の課題は、設定上の許可ではなく実効構成をどこまで確実に観測できるかである。とくに Codex CLI では、要求した名前付きエージェントと実際に起動したサブエージェントを常に同じ確度で証明できるとは限らない。確認できない情報は推測で補わず、未検証として Trace と利用者向けの表示に残す必要がある。

また、ランタイム設定による制限を唯一の安全境界と見なせるか、資格情報やサンドボックスの分離をどの範囲で併用するかは、運用を広げる前に決める。Skill、MCP、コンテキストの出所と版を継続して記録し、継承による想定外の能力を検出できることが、エージェント別運用を維持する前提となる。
